# NvContainer.exe: analysis of a packed, server-staged loader

| | |
|---|---|
| SHA-256 | `2512de03d705e3acabb057ca66aa74614a5c661988254428b09ad96c8f3debf6` |
| SHA-1 / MD5 | `24f32b4bf7443894f611032fdb28a17d5358f95d` / `df4097c658615e2233fb3bce067599ea` |
| Type | PE32+ x64, 830,464 bytes, unsigned, no version resource |
| Source | Discord CDN attachment |
| Analysed | 2026-11-24 |
| Method | Static analysis and Unicorn emulation. No stage was executed natively. |

**Summary.** The file uses the name of an NVIDIA component but is a packed loader for the DiscAuth
service. It unpacks a first stage in memory, elevates, and asks `discauth.net` for a second image that
the server relocates and links for the caller's memory. That second stage is a protected client for
the game Rust. Its readable code extracts Discord account names and IDs from Discord's memory,
reconfigures the Windows page file, starts a process and enumerates windows to hide one. Strings and
code are consistent with kernel memory access, injection, and searches for Microsoft Defender, Code
Integrity and ETW structures. It should not be run on a trusted machine.

Stage 1 is covered on the emulated path. In stage 2 the routines below were followed through the code
that is not virtualized; the rest was triaged from strings and imports, and the virtualized code was
not lifted. Statements are labeled **Confirmed** (observed in code or emulation), **Inferred** or
**Unknown**. Addresses are RVAs.

## Outer packer (Confirmed)

- Entry point `0x1FC30`. 49 encrypted `jmp r11` trampolines lead to the real stub at `0xA560`.
  Neighbouring functions inspected near the entry point are decoys.
- `0x207D0` decrypts `.data` in place from `0x52000`; `0x21C80` allocates `0x5AB98` bytes and copies
  the result; `0x22EF0` fills 105 import slots at `+0x3E000`; `0x296E0` makes `+0x1000` executable.
- The stub calls stage 1 at `+0x3470` with the constant `0x947424CB3A18CD6E`, later sent to the server
  as `StagingHash`.

## Stage 1 (Confirmed)

1. If not elevated, relaunches itself through `ShellExecuteExA` with `runas` and exits.
2. Sends an HTTPS POST to `https://discauth.net/Auth/LoaderMapper.capp` through one of three hardcoded
   addresses, with a browser User-Agent. Its mbedTLS configuration sets certificate verification to
   NONE.
3. Request type 1 sends `StagingHash`. The reply holds `Response`, `ImagedSize` and the import list.
4. Request type 2 sends the allocation's base address and the resolved import addresses. The reply
   holds `Entrypoint`, `MappedData` and `MappedSections`.
5. Copies the sections, marks code read/execute and calls the entry point.
6. Sleeps 10 seconds, frees the stage 2 allocation's base, then sleeps forever.

The server therefore receives the base address and import addresses and returns an image already
fixed up for that process. Stage 1 performs no relocation or import patching of its own.

### Wire format (Confirmed)

Bodies are encrypted under two 64-bit session keys chosen by the client. Both keys travel in the
request under a fixed outer key, so anyone holding the request plaintext can read both directions.
Fields are keyed by the CRC-32 of their names. `tools/transport.py` decodes both directions. Because
certificates are not verified, an intercepting proxy in a lab can recover the traffic.

The decoder was checked against requests generated by stage 1 under emulation and against two live
replies. The emulation replaced the HTTPS client with a local fake server, so TLS behavior comes from
static analysis. Stage 2 was obtained by replaying the two requests; the reply was saved and never executed.

## Stage 2

Image `0x95D000` bytes, 5 sections. A protector section at `0x3B1000` has entropy 7.92; `.text` branches
into it 1,945 times through 962 entries, and the `.pdata` region is encrypted. Most strings are built on
the stack from XORed bytes; some, including the WMI queries, are in plain text.

### Discord account extraction (`0x4E240`, Confirmed)

1. Looks for `Discord.exe`, `DiscordPTB.exe`, `DiscordCanary.exe` or the Development build, and opens the
   process with `PROCESS_ALL_ACCESS` (`0x4F1D8`).
2. Walks its memory with `VirtualQueryEx`, reading regions whose protection is read-only or read/write,
   within a time limit.
3. Searches each region for `{"_state":{`, reads `0x3FC` bytes around the match, and parses JSON.
4. Walks `_state` and `users`, and appends each `username` and `id` pair to the caller's vector.

No token field lookup was seen in this routine, and it writes nothing to Discord. It has no direct caller
in readable code, so the caller is probably virtualized. Where the list goes is **Unknown**.

### Page file reconfiguration (`0xBA280`-`0xBAC00`)

- **Confirmed:** WMI queries `SELECT * FROM Win32_ComputerSystem` and
  `SELECT * FROM Win32_PageFileSetting WHERE Name = '` in `ROOT\CIMV2`, with the property names
  `AutomaticManagedPagefile`, `InitialSize` and `MaximumSize`.
- **Inferred** from interface slot offsets: one path spawns a `Win32_PageFileSetting` instance, sets three
  properties and commits it. That would outlast the process, so check it on an affected machine.

### Hidden helper process (`0x12978F`)

- **Confirmed:** `CreateProcessA` with flags `0` or `CREATE_NO_WINDOW`, not suspended. Later code in the
  same routine looks for `win32u.dll` and `NtUserBuildHwndList`, then calls `GetWindowThreadProcessId`,
  `IsWindowVisible` and `ShowWindow`.
- **Confirmed:** it then calls `0xB35B0` and `0xB57A0`. Strings in those ranges include
  `Located Target ID`, `TargetProcessPEB` and `CreateThread`.
- **Confirmed:** the image lists stock Windows program names, including `colorcpl.exe`, `charmap.exe`,
  `dfrgui.exe`, `dccw.exe` and `LocationNotificationWindows.exe`.
- **Inferred:** it starts one of these, hides its window and injects into it. The link between the name
  list and this call was not traced.

them are cut or garbled, so that absence is not proof.

## Not covered

- Virtualized code, and 22 of 249 imports with no direct reference.
- The contents of the login request, and any driver or module downloaded after login.
- Whether the kernel and Defender code works; nothing was executed.

## Detection

| File | Contents |
|---|---|
| `rules/nvcontainer_discauth.yar` | Outer sample (file), unpacked stage 1 and the stage 2 Discord reader (memory) |
| `rules/proc_creation_nvcontainer_masquerade.yml` | Sigma: `NvContainer.exe` outside NVIDIA directories |
| `iocs.csv` | Indicators with confidence |

YARA results (yara-python 4.5.4): the outer rule matches the sample; the stage 1 rule matches both the raw stage 1
memory image and its rebuilt PE; the stage 2 rule matches the rebuilt stage 2 image it was derived from;
0 matches across 20,831 executables, DLLs and drivers under
`System32`, `Program Files` and `Program Files (x86)` on a Windows 11 machine (files over 60 MB skipped). The rules come from a
single sample and were not tested on variants or on a live process.
The Sigma rule's YAML was parsed but the rule was not run against event data.

The three IP addresses appear to be shared CDN addresses. Use the domain, not the IPs, for blocking.

## If this ran on a machine

The sample elevates and its second stage contains code aimed at the kernel, so treat the machine as
untrusted: disconnect it, check the page file settings, change passwords and sign out sessions from another device, and reinstall
Windows from clean media.

No samples or memory images are distributed here.
